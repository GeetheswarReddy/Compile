# Ticket T17: Make initialization and submission failures recoverable

Priority: P0
Status: Ready
Depends on: T16 findings for live verification; local work can begin immediately

## Evidence and problem

`image.png` exposes raw “Failed to fetch” next to an unstyled Retry button. The API client lets fetch exceptions propagate without context. Both baseline and practice submission paths need understandable pending, failure, quota, and recovery states. This ticket fixes interaction behavior; T18 supplies shared styling.

## Interfaces consumed

Existing API routes and payloads from T16; controlled code and question state; browser learner identity. Preserve the hook fields consumed by existing components.

## Interfaces produced

Existing API client methods and hook contracts with explicit, recoverable error behavior. Errors retain status and sanitized diagnostic metadata when available; absent HTTP responses are described as connectivity failures, not guessed CORS failures.

## Work and acceptance criteria

- Initialization failure offers an accessible retry and prevents actions that require an initialized learner; success clears stale errors without losing browser identity.
- Baseline and practice distinguish checking, incorrect answer, connectivity failure, server failure, and quota exhaustion. Pending actions prevent duplicate clicks and always exit pending state after failure.
- Preserve typed code and active question after failed submission; retry must submit the current code and question ID. Do not automatically retry execution POSTs, which can consume quota after an ambiguous response.
- Provide a bounded request timeout with cancellation handled separately from user-visible failure; aborted requests must not overwrite a newer screen.
- Quota exhaustion explains why execution is unavailable and leaves learning material viewable. Do not turn a transient server error into permanent read-only state.
- Handle baseline submission rejection without an unhandled promise rejection. Preserve the baseline resume point.
- Add focused mounted-flow tests for network failure then successful retry, server failure, pending duplicate prevention, and quota denial. Assert code/question preservation and actual request payloads.
- Verify both baseline submit and practice Run & Check against the repaired deployment with T21.
