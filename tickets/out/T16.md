# T16 — restore deployed submissions

Status: **Complete — deployed and verified**

## Outcome

The deployed submission failure was reproduced without consuming public quota. The existing `compile-v2-sandbox` Lambda returned `RuntimeError: execution sandbox unavailable` for a known-good seeded reference solution. Its matching CloudWatch event reported `execution sandbox initialization failed (error=RuntimeError)` before learner code ran.

The deployed source exactly matched the then-current built artifact (`CodeSha256` recorded during the audit; omitted here because it is operational metadata). This ruled out a stale deployment. The remaining initialization failure is the child `restrict_child()` call: AWS Lambda rejects installing the additional seccomp filter inside its runtime.

The proposed implementation adds a Lambda-only fallback. Outside Lambda, failure to install the kernel filter still fails closed. In Lambda, the fallback retains these boundaries:

- execution remains in the dedicated private sandbox Lambda;
- its VPC has no route or DNS and a deny-all network ACL;
- its role has no application data-service permissions;
- the child receives no AWS credentials or parent environment, only the runtime loader path;
- inherited descriptors are closed except the verdict pipe;
- CPU, address-space, file-size and process-count limits remain active;
- file opens and low-level process/network/import escape modules are denied in the child.

The Lambda fallback does not add this project's extra syscall-level seccomp filter because the runtime refuses it. That security-boundary change is why deployment now requires explicit user approval.
