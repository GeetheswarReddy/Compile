## Behavior and integration notes

- Initialization gates all route actions until it succeeds. Retry is in place, preserves the browser learner ID, clears stale errors on success, and ignores superseded responses.
- Baseline and practice use immediate ref locks as well as disabled controls, so two clicks in the same render cannot create duplicate submissions. Failed checks preserve the active question and typed code. Only an explicit quota response makes the UI read-only; connectivity and server failures remain retryable.
- Request cancellation is silent, while timeouts are user-visible retryable failures. Initialization and question-loading requests are sequenced so an older response cannot replace a newer screen. Active baseline submissions, practice checks, and generation requests are aborted when their screen unmounts.
- T18 should style `.app-initialization-error` and `.baseline-submit-error`, plus the existing alert/status, disabled, and checking states. The markup and accessible roles are already present.
- T19 should preserve the current controlled editor values and hook lifecycle when moving panels. `PracticeScreen` still receives the same `usePractice()` contract, and baseline submission errors now render inline with the active question rather than replacing the assessment screen.
- T20's CodeMirror integration is covered by the practice retry regression: the test locates the stable `.cm-editor` mount, dispatches the edit through its `EditorView`, and verifies the controlled code survives a failed request and is resubmitted unchanged. Baseline coverage continues to exercise its existing textarea.
